# Find-bugs report — 2026-08-04

## Critical bugs found: yes (2)

### 1) Org / custom-org profile updates wipe Stripe `is_premium`

**Impact:** A user with an active/trialing Stripe subscription who updates org fields (detach `org_code`, or set an incomplete custom org) had `users.is_premium` forced to `false`. Profile `premium` then dropped to false until another Stripe webhook re-synced — paid users lost entitlement.

**Root cause:** `routes/users.js` set `is_premium` from org state alone (`false` on detach; `hasCompleteCustomOrg` for custom org) without consulting active Stripe rows. Mirror of the Stripe→org stomp fixed in PR #6.

**Trigger:**
1. Complete Stripe checkout webhook → `is_premium=true`
2. `PUT /api/users/:id` with `{ org_name: "X" }` only (or `org_code: null` after attaching an org)
3. Before fix: `premium` becomes false despite `stripe_subscriptions` still `trialing`/`active`

**Fix:** Inject `stripeSubscriptionModel` into `createUserRoutes`; recompute `is_premium` as org-entitled **OR** active Stripe before writing.

### 2) Program create accepts any `pairing_id` (cross-couple injection)

**Impact:** Any authenticated user could `POST /api/programs` with another couple’s `pairing_id`. The program appeared in the victims’ program list (access is by accepted pairing membership) and could notify partners — therapy-content injection / authz bypass. Prompt sessions already enforced membership; programs did not.

**Root cause:** `routes/programs.js` `POST /` passed `pairing_id` straight into `createProgram` with no membership or existence check.

**Trigger:**
1. Couple A has an accepted pairing `P`
2. Outsider `POST /api/programs` with `{ user_input, pairing_id: P }`
3. Before fix: 201; victims see the outsider’s program under pairing access

**Fix:** Require non-deleted pairing and caller membership (`403` / `404`), matching prompt-session policy.
