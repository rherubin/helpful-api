# Find-bugs report — 2026-08-15 (UTC)

## Critical bug found: yes

### Bug and impact
Out-of-order Stripe webhooks could resurrect canceled premium. After `customer.subscription.deleted` set status to `canceled` and cleared `users.is_premium`, a delayed/retried `customer.subscription.updated` payload still carrying `status=active` (or `trialing`) was applied blindly. The row flipped back to active and `syncPremiumForUser` re-granted paid access with no live subscription.

### Root cause
`StripeBillingService.handleSubscriptionEvent` → `applyStripeSubscription` always upserted the event object. There was no terminal-status guard and no live Stripe reconcile on update events, so arrival order alone decided entitlement.

### Trigger
1. User completes Checkout → webhook writes `trialing`/`active` → premium true
2. Subscription canceled → `customer.subscription.deleted` → status `canceled`, premium false
3. Stripe retries an older `customer.subscription.updated` with `status=active`
4. Before fix: local row becomes active again and premium returns indefinitely
5. After fix: stale non-terminal update is ignored; status stays `canceled`, premium stays false

### Fix and validation
- Ignore non-terminal webhook payloads when the local subscription is already `canceled` or `incomplete_expired` (canceled Stripe ids are not reactivated).
- Regression: `testStaleSubscriptionUpdateDoesNotResurrectPremium` in `tests/stripe-billing-test.js`.
- Validation: restart API with `TEST_MOCK_LLM=true TEST_MOCK_PUSH=true TEST_MOCK_STRIPE=true`, then `npm run test:stripe-billing`.
