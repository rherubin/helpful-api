# Find-bugs report — 2026-08-08 (UTC)

## Critical bugs found: yes (3 new), fixed

### 1. Soft-delete leaves Stripe subscription billing active + webhook sync crash

- **Where:** `routes/users.js` `DELETE /:id`; `StripeBillingService.syncPremiumForUser` (~334) / `resolveUserIdFromSubscription` (~362); `User.getUserById` excludes soft-deleted rows
- **Trigger:**
  1. User completes Stripe Checkout → `trialing`/`active`, `is_premium=true`
  2. `DELETE /api/users/:id` (self soft-delete)
  3. Before fix: Stripe subscription stayed live (continued charging); later `customer.subscription.*` webhooks called `getUserById` which throws for `deleted_at IS NOT NULL` → webhook **400** forever
  4. Login-restore could leave stale premium (free access) or miss paid-state reconciliation (billed without premium)
- **Impact:** Deleted accounts keep getting billed; webhook pipeline permanently fails for that customer; premium state drifts across delete/restore
- **Confidence:** high
- **Covered by open PR themes (#12/#13)?** no
- **Fix:** Cancel active Stripe subscriptions on soft-delete; sync premium via `getUserByIdIncludingDeleted` + `setIsPremium`; resolve customer ids including soft-deleted rows; recompute previous owner when subscription row is reassigned; mock Stripe IDs are per-process unique so retained soft-deleted `stripe_customer_id`s do not collide after restart

### 2. Message update parent/child IDOR (step_id not bound)

- **Where:** `routes/programSteps.js` `PUT /programSteps/:stepId/messages/:messageId`
- **Trigger:**
  1. User authors message M on step B
  2. User retains access to unrelated step A (or only A after losing access to B)
  3. `PUT /api/programSteps/{A}/messages/{M}` with new content
  4. Before fix: access checked only for A; ownership checked only by `sender_id`; M on B was updated
- **Impact:** Tamper with own messages on programs/steps the caller is no longer authorized to access
- **Confidence:** high
- **Covered by open PR themes (#12/#13)?** no (adjacent to messages-stats IDOR theme, different endpoint)
- **Fix:** Require `message.step_id === stepId` (404 on mismatch) before ownership check

### 3. Admin JWT `expiresIn` treats env seconds as milliseconds

- **Where:** `AdminAuthService` constructor / `generateAccessToken` / `generateRefreshToken`
- **Trigger:**
  1. Set `JWT_ACCESS_TOKEN_EXPIRES_IN_SECONDS=86400` (as in `.env.example`)
  2. Admin login issues tokens with `expiresIn: "86400"` (string)
  3. `jsonwebtoken` interprets unit-less numeric strings as **milliseconds** → access token dies in ~86s; refresh JWT dies in ~20m while DB `expires_at` still says 14d
- **Impact:** Admin sessions randomly 401 after ~86s when standard env vars are set; refresh appears valid in DB but JWT verify fails
- **Confidence:** high
- **Covered by open PR themes (#12/#13)?** no (distinct from admin login `ReferenceError` / refresh delete bugs)
- **Fix:** `Number(...)` coerce env seconds before passing to `jwt.sign`
