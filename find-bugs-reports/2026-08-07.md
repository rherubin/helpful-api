## New bugs

### 1. `GET /api/org-codes` leaked redeemable `org_code` secrets (privilege escalation)

- **Location:** `routes/org-codes.js` `GET /` (pre-fix)
- **Trigger:**
  1. Any authenticated app user calls `GET /api/org-codes`
  2. Response included redeemable `org_code` strings (prompts were stripped; codes were not)
  3. Caller `PUT /api/users/:id` with `{ "org_code": "<leaked>" }` → `is_premium=true`
- **Impact:** Security — free premium / org entitlement for any account
- **Why new:** Not in the tracked list; directory listing was intentionally open, but redeemable secrets were not meant to be public
- **Fix:** Strip `org_code` (and prompts) for non-admin list responses

### 2. Pairing accept `max_pairings` TOCTOU race

- **Location:** `services/PairingService.acceptPairingByCode` / `models/Pairing.acceptPairingByPartnerCode` (pre-fix)
- **Trigger:**
  1. Requester ends up with multiple open partner codes (signup + concurrent `/request`, or leftover codes)
  2. Two acceptors redeem different codes concurrently
  3. Both pass non-transactional count checks, both accept → requester exceeds `max_pairings=1`
- **Impact:** Race condition / invariant break — multi-partner state despite cap
- **Why new:** Distinct from leftover-code cleanup (#8 / PR #5), which fixed sequential leftover redemption, not concurrent accepts
- **Fix:** `acceptPairingByPartnerCodeAtomic` — `SELECT … FOR UPDATE` on pairing + both users, re-check caps, accept, and soft-delete leftover invites in one transaction

### 3. Stripe Checkout double-bill gap before webhook (open session)

- **Location:** `services/StripeBillingService.createCheckoutSession`
- **Trigger:**
  1. `POST /api/billing/checkout` → session created (no `stripe_subscriptions` row yet)
  2. Immediately `POST /api/billing/checkout` again → previously succeeded (PR #8 only blocked when a local `trialing`/`active` row already existed)
  3. Complete both Stripe Checkouts → two live subscriptions / double charge
- **Impact:** Data/billing loss — double subscription charges
- **Why new:** Distinct from #4 / PR #8 (block when already subscribed). This is the pre-webhook / open-session window.
- **Fix:** Per-user row lock + reject when Stripe still has an `open` Checkout session for the customer (`409 checkout_already_open`)

### 4. Login underreported Stripe/org premium

- **Location:** `services/AuthService.login`
- **Trigger:**
  1. User gains premium via Stripe webhook or org entitlement (`users.is_premium=true`)
  2. `POST /api/login`
  3. Response set `premium` from pairing.premium only → `false`, while `/profile` and `/billing/status` correctly reported true
- **Impact:** User-facing breakage — web subscribers appear free after login; also leaked `bypass_password` / raw `is_premium`
- **Why new:** Not related to Stripe sync wipe or checkout double-sub bugs
- **Fix:** `premium: hasPremiumPairing || !!is_premium`; strip `bypass_password` and raw `is_premium` from login payload

### 5. Failed admin login crashes the API process (DoS)

- **Location:** `routes/admin-auth.js` `POST /login` catch block (~line 61)
- **Trigger:**
  1. `POST /api/admin/auth/login` with unknown email / wrong password
  2. `loginAdmin` throws into `catch`
  3. Catch references `email`, which was `const`-bound inside `try` → `ReferenceError`
  4. `server.js` `unhandledRejection` handler calls `process.exit(1)`
- **Impact:** Crash — entire API dies on a failed admin login attempt (trivial DoS)
- **Why new:** Distinct from ungated admin register (#1) and admin refresh rotation (#12)
- **Fix:** Destructure `email`/`password` from `req.body` outside the `try` block
