# Find-bugs report — 2026-08-06 (UTC)

## Critical bugs found: yes (3 new), fixed in a new PR.

### 1. Unauthenticated / ungated admin registration
- **Where:** `routes/admin-auth.js` `POST /api/admin/auth/register`
- **Trigger:** `POST /api/admin/auth/register` with any email/password while admins already exist and no opt-in env is set.
- **Impact:** Full admin takeover — create admin JWT, push-test any user, manage org codes, read soft-deleted PII lists / audit logs.
- **Fix:** Allow only when `ALLOW_ADMIN_REGISTRATION=true`, or `ADMIN_REGISTRATION_SECRET` matches, or zero admins exist (bootstrap). Test harness flags `TEST_MOCK_LLM` / `TEST_MOCK_STRIPE` also opt in.

### 2. Unverified IAP receipt grants premium
- **Where:** `services/SubscriptionService.js` `processReceipt`
- **Trigger:** Authenticated `POST /api/subscription` with attacker-chosen `expiration_date` (and minimal iOS/Android fields). No App Store / Play verification ran.
- **Impact:** Free pairing premium for any account; shared with partner via `reconcilePremiumStatus`.
- **Fix:** Require `TEST_MOCK_IAP=true` (mirror Stripe mock gate). Production without real IAP verification returns **503**.

### 3. Pairing GET IDOR (+ related ownership gaps)
- **Where:** `routes/pairing.js` `GET /api/pairing/:pairingId` (primary); also `routes/users.js` `GET /api/users/:id`, `server.js` `GET /api/messages-stats`
- **Trigger:** Any JWT + another user’s `pairingId` → full pairing row including live `partner_code` and member emails. Accept the stolen code via `POST /api/pairing/accept` to hijack a pending invite. Cross-user profile GET and messages-stats by `programId` similarly lacked ownership checks.
- **Impact:** Pairing hijack / PII leak / cross-user engagement stats.
- **Fix:** Membership gate on pairing GET; self-only on user GET; `checkProgramAccess` on messages-stats.

### Near-misses discarded
- Concurrent Stripe checkout TOCTOU (two parallel checkouts before webhook) — real race but sequential double-checkout already blocked (PR #8); harder to trigger reliably than client-trusted IAP
- Concurrent pairing accept past `max_pairings` — TOCTOU on count-then-accept; SQL accept is atomic per code; leftover invites cleaned after accept
- `GET /api/org-codes` listing redeemable codes — intentional product picker (covered by org-code tests)
- Login response `premium` omitting `user.is_premium` — display inconsistency only; profile endpoint is correct
