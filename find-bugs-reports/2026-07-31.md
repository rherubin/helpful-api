# Bug scan — 2026-07-31

## Critical bug found: yes

### Bug and impact
Soft-deleting a pairing (or cascading soft-delete via user delete) did **not** revoke the former partner’s access to shared programs, program steps, or messages. Therapy content remained readable through `GET /api/programs` and `GET /api/programs/:id` (and the matching step/message access checks) even though the pairing was no longer active.

### Root cause
`Program.getUserPrograms`, `Program.checkProgramAccess`, `ProgramStep.checkStepAccess`, and `Message.checkMessageAccess` authorized partner access with `pair.status = 'accepted'` but omitted `pair.deleted_at IS NULL`. Prompt-session access already enforced the soft-delete filter; the program path did not.

### Fix and validation
- Require `pair.deleted_at IS NULL` alongside accepted status in the four access queries above.
- Owners keep access via `programs.user_id`; only pairing-based partner access is revoked.
- Added pairing-lifecycle coverage: partner can read a paired program while accepted, then gets 403 / list exclusion after soft-delete; owner still reads successfully.
- Validation: `TEST_MOCK_LLM=true npm run test:pairing-lifecycle` — **30/30 passed**.
