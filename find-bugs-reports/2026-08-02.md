## New bugs fixed

### 1. Admin refresh always fails (`deleteTokenByUserId` missing)

- **Location:** `services/AdminAuthService.js` → `verifyAndRefreshTokens`
- **Trigger:** Admin calls `POST /api/admin/auth/refresh` with a valid refresh token
- **Impact:** Always 401; newly inserted refresh row is orphaned. Repeat logins accumulate rows; `getTokenByUserId` is nondeterministic across multiples
- **Root cause:** Called nonexistent `refreshTokenModel.deleteTokenByUserId()` *after* `issueTokensForAdminUser()`. Even the correctly named delete-by-user helper would wipe the just-created token if invoked after issue
- **Fix:** Delete admin refresh rows *before* issuing replacements; clear prior tokens on `loginAdmin` too

### 2. FCM `mismatched-credential` auto-prunes valid device tokens

- **Location:** `services/PushNotificationService.js` → `FCM_DEAD_TOKEN_CODES`
- **Trigger:** Deploy wrong/staging Firebase credentials (or FCM API misconfig) then send any push (`pairing_accepted`, step message, admin `push-test`, etc.)
- **Impact:** Valid `device_tokens` rows deleted for every affected user; push delivery silently stops until clients re-register
- **Root cause:** Config/project mismatch treated as a permanently dead token
- **Fix:** Remove `messaging/mismatched-credential` from the dead-token set; keep only true dead-token codes

### 3. Soft-delete permanently locks email / blocks recovery after token expiry

- **Location:** `models/User.js` (`getUserByEmail`, `softDeleteUser`), `services/AuthService.js` (`login`), `routes/users.js` (`PATCH /:id/restore`)
- **Trigger:** Soft-delete account → wait for access token expiry → try login / re-register / restore
- **Impact:** Permanent account + email lockout. Login excludes soft-deleted rows; UNIQUE email blocks re-register; restore requires a live JWT
- **Root cause:** Soft-delete retained UNIQUE email without a credentials-based recovery path
- **Fix:** Revoke refresh tokens on soft-delete; `POST /api/login` with correct password auto-restores (`data.restored: true`)

### 4. `max_pairings=1` bypass via leftover signup partner codes (+ restore)

- **Location:** `services/PairingService.js` (`acceptPairingByCode`), `models/Pairing.js`, signup auto-pending in `routes/users.js`
- **Trigger:** Alice + Bob sign up (each gets pending code). Alice accepts Bob’s code. Carol accepts Alice’s leftover signup code → Alice has 2 accepted pairings. Related: soft-delete pairing, rematch, restore old pairing also exceeded max
- **Impact:** Breaks one-pairing invariant; multi-partner state
- **Root cause:** Accept checked only acceptor’s count; leftover open partner-code invites were not invalidated; restore had no max check
- **Fix:** Enforce requester max on accept; soft-delete both members’ open partner-code invites after accept; block restore when a member is at cap or deleted

### 5. Any authenticated user could list all soft-deleted users/pairings

- **Location:** `routes/users.js` `GET /deleted/all`, `routes/pairing.js` `GET /deleted/all`
- **Trigger:** Any user JWT against those endpoints
- **Impact:** Mass PII disclosure (emails, names, pairing membership)
- **Root cause:** Auth-only, not admin-gated
- **Fix:** Require `req.user.type === 'admin'` (regular JWTs → 403)
