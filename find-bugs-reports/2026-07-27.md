# Find-bugs report — 2026-07-27

## Critical bug found: yes

### Bug and impact

**User soft-delete / restore IDOR** in `DELETE /api/users/:id` and `PATCH /api/users/:id/restore`: any authenticated user could soft-delete or restore **any** other user. Soft-delete cascades to that user’s pairings, so an attacker could wipe another account’s pairings (and hide the account from normal lookups) without consent.

**Related:** `PATCH /api/pairing/:pairingId/restore` accepted any authenticated caller (not membership-gated), so an outsider could restore a pairing members had soft-deleted.

### Root cause

Delete/restore handlers authenticated the caller but never compared `req.user.id` to the target resource owner/members. `PUT /api/users/:id` and `DELETE /api/pairing/:id` already enforced ownership/membership; soft-delete paths did not.

### Fix and validation

- Gate user soft-delete and restore to self (`id === req.user.id`).
- Gate pairing restore to former members via `getPairingByIdIncludingDeleted` + membership check.
- Inject `pairingModel` into `createUserRoutes` (drop `app.locals.pairingModel` service-locator).
- Preserve not-found errors / LEFT JOIN on `getPairingByIdIncludingDeleted` for pending invites.
- Tests: outsider 403 assertions in `user-soft-delete-test.js` and `pairing-lifecycle-test.js`.
- README updated to document self/member gating.
