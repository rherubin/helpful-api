# Find-bugs report — 2026-08-05 (UTC)

## Critical bug found: yes

### Bug and impact
`POST /api/billing/checkout` created a new Stripe Checkout session even when the caller already had a `trialing` or `active` row in `stripe_subscriptions`. A user (or buggy client) who completed checkout once could start Checkout again, pay a second time, and end up with two live subscriptions — double billing.

### Root cause
`StripeBillingService.createCheckoutSession` always called `stripe.checkout.sessions.create` after ensuring a customer. It never consulted `stripeSubscriptionModel.getActiveForUser` before opening Checkout. Plan changes are supposed to go through the Customer Portal.

### Trigger
1. Complete Checkout + `checkout.session.completed` webhook → subscription `trialing`/`active`
2. `POST /api/billing/checkout` again with a valid plan
3. Before fix: 200 + new Checkout URL (second charge possible)
4. After fix: **409** with guidance to use the billing portal

### Fix and validation
- Reject checkout with **409** when an active/trialing Stripe subscription already exists.
- Regression coverage in `tests/stripe-billing-test.js` (`testCheckoutBlockedWhenSubscriptionActive`).
- Reordered disallowed-origin check to run before the user is subscribed so 409 does not mask 400.
- Portal test no longer opens a second checkout (customer id already set by the first session).
